## Product boundary
Visual Atlas is the shared, host-neutral artwork authority: stable asset IDs, original textures, regions, sequences, state sets, compositions, slots, typed inputs, spatial height/views/wind, license and publication/visual QA. Hex World is the authoritative spatial world and presentation host: cells, geometry, materials, climate, water, placement, scatter, lighting, collision, movement, editor commands and saves. Interactive Tabletop owns D&D rules, characters, actions, inventory, encounters and permissions; it should eventually consume a supported Hex World host API, not fork the renderer or store a second world. AI is a builder client of the same validated edit-plan pipeline, not an alternative engine.

## Compatibility is per role, not a universal yes/no flag
Discover the approved archive in Atlas public-catalog.json, resolve the stable asset ID and archive_sha256, validate the actual ZIP and reachable asset graph, adopt supported spatial metadata, validate the specific host role and preview the real render. Distinguish published/structurally valid, host-loadable, role-qualified and artist-reviewed. Capability hints are derived discovery metadata, not proof of host support.
- Upright object: transparent region/sequence/state_set or supported fixed-canvas composition, matched logical canvas and root pivot, explicit world scale, compatible state/view inputs. Current host supports billboards and six views at 35.264° elevation; new camera alignment needs angle qualification for asymmetric art. No arbitrary manifest code.
- Terrain top/side and transition mask: static seamless unprojected measured region, opaque appropriate grayscale/RGB/albedo (mask grayscale), host repeat and material mapping. Do not use a complete baked hex diorama.
- Scatter: qualified upright asset plus host family rule (materials, density, size, spacing, slope, surface conditions, LOD, season/contact/shadow); decorative until explicitly promoted. Wind from spatial profile or deliberate host override. No automatic physics based on tags.
- Interactive: supported composition or state set, explicitly declared inputs/states/slot options and behavior event; host owns collider, reach, authorization and gameplay. A static chest picture is not an openable chest.
- Water, fire, glow and emissive art: current host has procedural water and lighting; animated sprites can load via existing object route. Dedicated texture/effect/emissive roles need explicit adapter work, no fabricated compatibility.

## Milestones (in priority order)
1. Production asset bridge. Inventory the seven approved fantasy preview collections (53 asset records: 52 regions, one state set). Build an actual-archive qualification matrix by role, including failure reasons, license, digest, scale and pivot. Pin representative published grass, shrub, tree and fern to a Hex style using the existing smi-hex-style/1 contract. Add optional world-environment catalog browsing defaults and useful role filters/preview, not a duplicate catalog. Verify exact public archive through browser loading, place/rotate/save/reload and real scene capture. Published previews are artistic QA pending; do not mark them production-ready automatically. Resolve stable archive URL retention/versioning before depending on long-lived saves; a hash alone detects changes but cannot recover an overwritten archive.
2. Art direction pilot. Create a coherent woodland/river/ruin environment, first with existing compatible artwork and clearly marked fixture ground textures until real seamless terrain is ready. Author production terrain/top/side materials, masks, grass and foliage variants, stone/ruin/architecture, matched water/effect art, and one actual directional interactive chest. Qualify 30° vs legacy alignment before producing asymmetric sets at scale; retain existing IDs and physical camera convention, specify explicit angle metadata only if needed. Inspect all six views, transitions, lighting, seasons and collision/interaction. No bulk artwork generation before pilot review.
3. Builder usability. Consolidate the lab into a tool palette + inspector + world view. Asset search, thumbnails, compatible role assignment, saved style/palette presets, proper ghost previews, selection/paint/path/grade/grove controls. Reuse existing edit-plan, history, prefab and art-style contracts. Add scene-template capture for components, repeatable placement and multi-level ramps/bridges/paths with verified support. A user should create a small complete scene without hand-editing JSON.
4. Scalability and reliability. Measure on user hardware and repeatable reference scenes (startup, idle, pan, zoom, edit, dense vegetation). Distinguish CPU stage time, GPU timing where supported, frame interval, visible instances, memory, texture upload and draw count. Move to chunk-based packed geometry, bounded sprite/raster caches, shared texture batching and LOD, avoid drawing offscreen/hidden work; evaluate with comparable scenes and quality. Prioritize stable 30 FPS at chosen target hardware before broadening world scale (target, not current guarantee). Plan durable chunk and asset retention; no save corruption or silent unknown-to-air conversion.
5. Environment depth. Implement independent deterministic animation phases, wetness/precipitation and seasonal host mappings where justified, water/vegetation/fire/contact coupling, local light occlusion and emissive masks. Preserve authored fixed waterways as low-cost default. Effects/visual clock must never mutate simulation implicitly. Extend supported Atlas inputs/bindings, not new asset kinds.
6. Unified authoring and shared command interface. After the Phase 5 review, consolidate editor tools; evolve existing prefab placement to plan foundations, explicit excavation, clearance, rotation and surface/grid depth adjustment. Add catalog focus/search commands and a single validated command contract for manual and AI clients.
7. General game runtime and permissions. Separate editor and gameplay presentation from the same authoritative world. Expose host lifecycle, scoped commands, entity ownership, movement, interactions, visibility and application-owned HUD bindings. Support single-player local hosts as well as authoritative multiplayer deployments; never rely on hiding controls for authorization.
8. AI-assisted building. Use the shared command interface for both non-mutating UI assistance and reviewed world construction. Export bounded context and compatible palette; generate ordinary proposed edit plans, preview, report conflicts, approve and undo. No unrestricted execution or autonomous publication.
9. Interactive Tabletop and reusable game templates. Integrate one encounter through the generic host and application rules adapter; retain D&D rules in Tabletop. Validate reuse with a non-D&D single-player game example. See PRODUCT_VISION.md for the agreed direction.

## First acceptance scene
A small painterly woodland clearing with a trail, fixed animated creek, grass/understory, several trees, seasonal fern, a placed chest and a torch. Verify asset discovery and exact archive digest, ground anchors and scale, camera selection and rotation, scatter/season/wind, fixed water with frozen simulation, manual edits and reversible plans, and save/reload. Use the existing static chest previews as decoration only; separately author a genuinely interactive one. Distinguish fixture vs production art. Record screenshots, compatibility status and comparable measured frame timings. The first scene is successful only when the actual assets load and the workflow works end to end; publication alone is insufficient.

## Release discipline
Atlas agents create and qualify artwork using its existing publication workflow, canonical pack schema and exact archive receipts. Hex World agents extend host adapters only when role requirements justify it; no duplicate manifest, texture store or renderer. Batch changes and qualify once per coherent milestone. Keep backwards compatibility explicit, report pending/unsupported capabilities, and never imply that deployment passed until the Pages workflow confirms it.

## Phase 5 review gate (scope boundary)
Stop at Phase 5 before starting Tabletop integration or AI builder implementation. A review candidate must demonstrate the same reproducible authored clearing through all six camera views, exact pinned assets and save/reload, complete manual building without JSON, supported directional interactive prop, authored terrain, target-device performance evidence, deterministic visual phases, explicit climate responses and water/fire/contact/lighting behavior. Distinguish staged, tested, deployed, role-qualified and artistic-approved work; never convert a preview into a production claim. Atlas retention (issue #47), production terrain/directional art, target-hardware results, local-light occlusion and emissive masks are explicit remaining dependencies. At the checkpoint evaluate a single world host for editor/play mode; reusable content via Atlas; scoped Tabletop adapter; proposed edit-plan clients; deployment and persistence scale. Do not widen scope until those evidence and boundary decisions are reviewed.
